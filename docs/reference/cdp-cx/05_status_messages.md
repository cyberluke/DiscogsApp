# Sony CDP-CX S-Link Reference Specification

# 05. Status Messages

Version: 1.0

Status: Reference

---

# Purpose

This document describes every known status message generated by Sony
CDP-CX changers.

Unlike commands, status messages are generated by the player itself.

Applications should primarily react to these events rather than assuming
commands always succeed.

---

# Packet Format

General format

```
98 SS [payload...]
```

where

98

Player 1

SS

Status Identifier

payload

Status-specific information

# 0x00 Play

Packet

```
98 00
```

Meaning

Player entered PLAY state.

This message is rarely relied upon because

```
0x50
```

contains significantly richer information.

---

# 0x01 Stop

Packet

```
98 01
```

Meaning

Playback stopped.

Runtime SHOULD

enter

Stopped

state.

---

# 0x02 Pause

Packet

```
98 02
```

Meaning

Playback paused.

Track position is preserved.

---

# 0x06 Carousel Moving

Packet

```
98 06
```

Meaning

Carousel is rotating.

Disc retrieval is currently in progress.

Typical sequence

```
Play Disc

↓

54 Loading

↓

06 Moving

↓

58 Loaded

↓

50 Track Status
```

Applications SHOULD NOT assume

06

always appears.

---

# 0x08 Ready

Packet

```
98 08
```

Meaning

Player ready.

No mechanical movement.

Safe to accept commands.

Ready

does not necessarily mean

Stopped.

---

# 0x0C Track Ending

Packet

```
98 0C
```

Meaning

Approximately

30 seconds

remain.

Generated only while playing.

Useful for

display updates

or

preloading next track.

Applications SHOULD NOT use this packet alone for playlist advancement.

---

# 0x18 Door Open

Packet

```
98 18
```

Meaning

Front door opened.

Applications SHOULD immediately invalidate

cached disc state.

Expected sequence

```
Door Open

↓

Scanning

↓

Model

↓

Ready
```

---

# 0x2E Power On

Packet

```
98 2E
```

Meaning

Player powered on.

Usually followed by

```
61

↓

58

↓

52

↓

08
```

Applications SHOULD rebuild internal state after Power On.

---

# 0x2F Power Off

Packet

```
98 2F
```

Meaning

Player powered off.

Applications SHOULD discard

transport state

while retaining

library metadata.

---

# 0x50 Track Status

Packet

```
98 50 DD TT MM SS
```

Parameters

DD

Disc Number

TT

Track Number

MM

Track Length Minutes

SS

Track Length Seconds

Example

```
98 50 62 14 02 14
```

Meaning

Disc

62

Track

14

Length

2m14s

Example

```
98 50 CA 03 03 48
```

Disc

148

Track

3

Length

3m48s

This is the

single most important packet

generated by the player.

Applications SHOULD derive

Now Playing

from this packet.

---

# 0x52 Display Disc

Packet

```
98 52 DD
```

Meaning

Front panel currently displaying

Disc DD.

This packet does

not

necessarily indicate playback.

Useful while browsing.

---

# 0x54 Loading Disc

Packet

```
98 54 DD
```

Meaning

Mechanical retrieval started.

Disc arm is moving.

Applications SHOULD enter

Loading

state.

---

# 0x58 Disc Loaded

Packet

```
98 58 DD
```

Meaning

Requested disc has reached

play position.

Playback may begin immediately afterwards.

Applications SHOULD transition

Loading

↓

Loaded

rather than directly

↓

Playing.

---

# 0x61 Model Identifier

Packet

```
98 61 XX YY
```

Byte 2

Capacity

Known values

```
00

100 Disc
```

```
FE

200 Disc
```

Byte 3

Model Identifier

Commonly

```
0B
```

Example

```
98 61 FE 0B
```

Meaning

200 Disc Changer

Model

0B

Applications SHOULD cache this information once.

# 0x70 Player Status

Packet

```
98 70 00 SS 00 DD 00
```

This packet reports

global playback mode.

# Runtime Use

Applications SHOULD use

70

for

global mode

only.

Track information should always come from

50.

# Runtime Recommendations

Treat

50

as

authoritative

for

Now Playing.

Treat

70

as

authoritative

for

playback mode.

Treat

61

as

static configuration.

Treat

54

and

58

as

mechanical events.

# Events

Recommended semantic events

```
PowerOn

PowerOff

DoorOpened

LoadingStarted

LoadingCompleted

TrackStarted

TrackChanged

Ready

PlaybackModeChanged

ModelDetected
```

The remainder of the application should never interpret raw status bytes.
